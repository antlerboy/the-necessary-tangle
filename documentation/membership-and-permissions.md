# Membership and permissions

The Necessary Tangle welcomes serious contribution without pretending that open participation and unrestricted write access are the same thing.

The public membership form prepares a GitHub Issue. It does not grant rights. The curator decides whether a proposed role, task and permission fit the actual work.

## Participation levels

### Participant

Participants read, discuss, ask questions, report faults and propose material. They need no repository permission.

### Contributor

Contributors submit corrections, sources, draft entries, comparison notes, code or documentation. Work normally arrives through Issues or pull requests. Contributors do not publish directly.

### Research collaborator

A research collaborator takes responsibility for a bounded batch: a named corpus, archive, source register, lineage, interface change or validation task. Scope and completion tests are agreed before broad access is granted.

The normal GitHub permission is `triage` or `write`, and only where it saves real friction. A branch-limited pull-request workflow is preferred to direct changes on `main`.

### Domain steward

A domain steward reviews a named area. The role includes testing definitions, relation types, source quality, counter-evidence and important rival accounts. A steward recommends acceptance, revision, dispute or deferral. The role does not confer unilateral release authority.

The normal GitHub permission is `write` or `maintain`, granted individually.

### Curator

The curator holds responsibility for the public boundary, permissions, accepted wording, merges, releases and the record of disagreement. Benjamin P Taylor is the founding curator.

## Permission mapping

GitHub's permissions are coarse. Project roles are not badges automatically mapped to maximum access.

| Project role | Normal GitHub permission | Main-branch merge |
|---|---|---|
| Participant | None | No |
| Contributor | None | No |
| Research collaborator | Triage or write when needed | No |
| Domain steward | Write or maintain when granted | By reviewed pull request only |
| Curator | Admin | Yes, after validation |

The curator may grant a lower permission, limit work to a branch or issue, set a trial period, require a second reviewer, or withdraw access.

## LLMs, agents and automation

An LLM or automation does not become a member in its own right. It operates through a human sponsor.

Every automated contribution must identify:

- the human sponsor;
- the model, agent or tool where it materially generated or transformed content;
- the sources supplied to it;
- the transformation performed: extraction, comparison, summary, inference, drafting or code generation;
- what a human checked;
- unresolved uncertainty.

The automation may use no greater permission than the sponsor. It may not merge, release, grant access, settle disputes or silently rewrite evidence status.

The sponsor remains accountable. The curator remains responsible for publication.

## What an application should contain

A useful request names:

- the requested role;
- the GitHub account;
- the bounded domain or corpus;
- a concrete first contribution;
- relevant experience and recognised limitations;
- the human sponsor where automation is involved;
- acceptance of the code of conduct, source rules and licensing terms.

The first contribution is normally the test. Titles follow demonstrated work rather than arriving in advance of it.

## Review and withdrawal

Permissions should be reviewed after the first batch and periodically thereafter. They can be narrowed or removed where work is inactive, outside scope, unsafe, untraceable or repeatedly bypasses review.
